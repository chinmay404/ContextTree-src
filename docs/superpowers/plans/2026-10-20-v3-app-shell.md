# V3 App Shell Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build everything around the V3 board from the approved mockups: the public landing (A), sign-in (B), the boards home (C), the account menu (D), the settings sheet with API keys (E) and the avatar on the board (F). V3 board turns run on the user's own key for all seven providers, and the first-visit welcome tour is wired in.

**Architecture:**
- **Shell.** It lives in `components/shell/` on the integration branch. Board data goes only through `EngineApi`, so FastAPI stays the single writer.
- **Keys.** They go through the existing V2 key store (`/api/user-api-keys`, AES-GCM in `lib/byok-crypto.ts`). The store is widened from 3 to 7 V3 providers, and each key gets a real provider check. The result is kept in the row's existing `metadata` jsonb.
- **Engine.** On a V3 turn it resolves the chat's model through a new key-only resolver (`app/agent/helpers/v3_llm.py`). It uses the user's stored key for that model's provider and never a server env key. V2 turns keep `get_llm` unchanged. A missing or refused key comes back as a coded error. The board shows it as "Add your <Provider> key", with a button to the keys sheet, and re-asks once the key is saved.
- **Pebble maps.** Boards outside the canvas are React SVG maps built from a tiny `preview` that the engine adds to `GET /boards`.
- **Landing.** It is server-rendered. Its boards are the real `<Board>` in a read-only `showcase` mode, fed by an in-memory API.

**Tech Stack:** Next.js 16 (app router, server components), NextAuth v4 (Google, database sessions), React 19, vitest (node and jsdom), Playwright, FastAPI with LangChain chat clients (`langchain_anthropic`, `langchain_openai`, `langchain_google_genai`, `langchain_groq`) and psycopg2. No new npm dependency: the key checks use plain `fetch`, as the owner asked.

**Spec:** `docs/design/v3-app-shell-mockups.html`, including its design-plan comment. Decisions: `context/DECISIONS.md`, rows 59, 60 and 63. Owner answers of 2026-10-20 (logged in "Owner decisions" below). Tour spec: `docs/design/onboarding-tour.html` (the tour is built, v3 `f127fee`). Direction and anti-goals: `context/DIRECTION.md`. ## Global Constraints

- The browser never calls FastAPI directly. All board reads and writes go through `EngineApi` and `/api/engine/*`.
- Never send a saved key back to the browser. Responses carry only `last4`, `status`, `checkedAt`, `updatedAt` and the existing `keyHint`. Never log a key, and never put one in an error message, an exception string or an SSE frame.
- Keys stay in the V2 store: table `user_api_keys` and `lib/byok-crypto.ts` (Next encrypts; the engine decrypts with `app/agent/helpers/byok.py`). Do not add a migration.
  - Check results go in `metadata.keyCheck = { status, checkedAt }`.
  - V2's `BYOK_PROVIDERS` (`openai`, `anthropic`, `litellm`) and the V2 dialog and model panel built on it stay as they are.
  - V3 adds `V3_KEY_PROVIDERS` alongside.
- **V3 turns use the user's key only.** Every LLM call made for a V3 board turn takes its key from `get_user_provider_api_key(email, provider)`. That covers the answer, the conversation summary and the branch-start summary. No `os.getenv("<PROVIDER>_API_KEY")` on that path. V2 turns (`boardId` absent) keep `get_llm`, `validate_model_access` and `_byok` exactly as they are.
- **What still runs on server keys (owner Q1):** ingest (source overviews via `SUMMARY_MODEL_NAME`, embeddings) and web search. These are not model turns.
- Model ids come only from `MODELS` in `components/board/lib/catalog.ts`. The engine's `V3_ROUTES` must have exactly one route per `MODELS` id; a test pins this in each repo. Labels: `Claude`, `GPT`, `Gemini`, `Llama (Groq)`, `DeepSeek`, `Mistral`, `Kimi`.
- Export is not built. "Export my boards" is disabled with a "Soon" chip, as is "Export & data" in the settings nav. The landing never mentions Markdown or export.
- The founder's note is a placeholder for the owner: the mockup draft, signed `— [Founder's name]`.
- Never use `innerHTML` with user or seed text. Use React text nodes. Board-engine DOM strings go through `esc()` (`components/board/lib/format.ts`). Seed answers are markdown, rendered by the board's `markdown.ts`.
- Pebble look:
  - Bricolage Grotesque via `bricolage` (`components/board/fonts.ts`).
  - Token values copied from `components/board/pebble.css` into `components/shell/tokens.css`, pinned by a parity test.
  - Light only. No dark surfaces, no gradient text, no three identical feature cards.
- The landing (`/`, `/landing`) and the boards home must work at 390 px with no horizontal page scroll.

- The landing is public. It renders on the server (readable with JS off) and has SEO metadata. Sign-in is NextAuth Google only.

## Review Focus

1. **A V3 turn quietly uses a server env key.** The user has no key for the chat's provider while `ANTHROPIC_API_KEY` (etc.) is set in the engine env. Expected: 400 `missing_key` naming the provider; no provider call is made. That holds for the answer, the rolling summary and the branch-start summary. Tests in Tasks 6 and 7.
2. **A saved key leaks back.** The raw key or its ciphertext shows up in a GET, POST or check response, an error, a log, an SSE frame or the DOM after saving. Expected: only `last4` and status. Tests in Tasks 14, 15 and 18.
3. **A brand-new user asks the first question with no key.** Expected:
   - The sheet opens on API keys, and the question is kept.
   - Saving any working key creates the board with that provider's model and asks the question.
   - Closing the sheet without a key keeps the text and says why.
   - Test in Task 21.
4. **The provider is slow or down during a key check.** Expected: after at most 5 s the status is `unchecked`. The key is saved, is not marked rejected, and the row says "Saved · couldn't check it just now". Tests in Tasks 14 and 15.
5. **Hostile or very long board titles and chat names** in maps, recents, list rows and menus. Expected: literal text, truncated with "…", no layout break at 390 px. Tests in Tasks 12 and 19.
